Strapi-5-Plugins auf mehreren Instanzen betreiben

Schero D. · 11. November 2026

Zwei Railway-Replicas mit je vier pm2-Workern sind acht Strapi-Prozesse, die eine Datenbank teilen und keinen Speicher. Ein Plugin, das im Speicher zählt, sperrt oder plant, tut das achtmal. Das sind die Muster, die die Plugins auf dieser Seite stattdessen nutzen, mit den Zahlen aus ihren Tests.

  • Geteilten Zustand in die Datenbank legen
  • Bedingt schreiben statt erst zu lesen
  • Nur dort sperren, wo Lesen-Ändern-Schreiben nötig ist
  • Hintergrundjobs unter einer Lease ausführen
  • Outbox-Zeilen beanspruchen, damit jede Nachricht einmal rausgeht
  • Kurze, dokumentierte Fenster für Caches akzeptieren
  • Jedem Prozess dieselben Secrets geben
  • Die echte Client-IP durch den Proxy reichen
  • Bei Schemaänderungen mit einer Replica starten
  • Socket.IO braucht einen Adapter

Geteilten Zustand in die Datenbank legen

Jeder Wert, über den sich zwei Prozesse einig sein müssen, liegt in der Strapi-Datenbank: Rate-Limit-Zähler, Kontingente, Widerrufe, Leases und Outbox-Zeilen. Magic Link, Magic Mail, Magic Session Manager und Magic MessageGate brauchen deshalb keine Sticky Sessions, Redis ist optional. Requests dürfen auf jedem Prozess landen.

Bedingt schreiben statt erst zu lesen

Lesen und danach Schreiben verliert Updates, wenn zwei Prozesse es gleichzeitig tun. Die Plugins schreiben in einer Anweisung und lassen die Datenbank entscheiden. Magic Mail reserviert Kontingent mit einem UPDATE ... WHERE count < limit pro Versand und zählt Öffnungen mit SET count = count + 1. Magic Link akzeptiert einen Login-Link oder Code per bedingtem Update, also genau einmal über alle Prozesse.

Nur dort sperren, wo Lesen-Ändern-Schreiben nötig ist

Magic Link schreibt seine Plugin-Store-Schlüssel (JWT-Sperrliste, IP-Sperren, Einstellungen) unter einem clusterweiten Lock: pg_advisory_xact_lock auf PostgreSQL, GET_LOCK auf MySQL und die Schreibsperre von SQLite. Heiße Pfade bleiben ohne Lock. Bis Version 6.1 hängte jeder Login an eine gemeinsame Sessionliste unter diesem Lock an. Version 6.2 speichert stattdessen eine Zeile pro JWT. Mit 4 Prozessen auf PostgreSQL 16 und 100 gleichzeitigen Logins, während der alte Lock 5 Sekunden gehalten wurde, brauchte 6.1 5,5 s und 6.2 0,38 s.

Hintergrundjobs unter einer Lease ausführen

Jeder Prozess behält seine Timer, aber jeder Lauf einer Bereinigung, Kontingent-Erneuerung oder Migration holt sich zuerst eine Lease in der Datenbank. Ein Prozess erledigt die Arbeit pro Intervall; fällt er aus, übernimmt ein anderer beim nächsten Takt. Magic Mail und Magic Link arbeiten so.

Outbox-Zeilen beanspruchen, damit jede Nachricht einmal rausgeht

Magic MessageGate beansprucht Outbox-Nachrichten mit FOR UPDATE SKIP LOCKED auf PostgreSQL und MySQL 8 und mit einem bedingten Update auf SQLite. Im Test sendeten 8 Prozesse auf einer PostgreSQL-Datenbank hinter einem Round-Robin-Balancer 500 Nachrichten ohne ein einziges Duplikat. Ein Versand mit unbekanntem Ergebnis wird als unsicher markiert und wartet auf einen Admin, statt durch Wiederholung doppelt zugestellt zu werden.

Kurze, dokumentierte Fenster für Caches akzeptieren

Manche Lesezugriffe werden pro Prozess gecacht, und die Verzögerung steht in der Doku. Bei Magic Link erreicht ein Widerruf die anderen Prozesse innerhalb von 2 Sekunden und geänderte Rate-Limit-Einstellungen innerhalb von 5 Sekunden. Magic Mail prüft seine Einstellungszeile etwa einmal pro Sekunde.

Jedem Prozess dieselben Secrets geben

Ein Prozess mit anderem JWT_SECRET lehnt Tokens der anderen ab, und ein anderer Verschlüsselungs­schlüssel kann gespeicherte Zugangsdaten nicht lesen. Magic Mail schreibt beim Start kurze Fingerprints seiner Secrets ins Log; zeigen zwei Instanzen verschiedene Werte, sind ihre Secrets verschieden.

Die echte Client-IP durch den Proxy reichen

Hinter Railways Edge oder einem Load Balancer gehört proxy: { koa: true, maxIpsCount: 1 } in config/server.js. Ohne das teilen sich alle nicht angemeldeten Aufrufer die Adresse des Proxys und damit ein einziges Rate-Limit-Kontingent.

Bei Schemaänderungen mit einer Replica starten

Strapi legt Tabellen beim Start an und ändert sie, und dieser Schritt ist zwischen Prozessen nicht abgestimmt. Auf einer leeren Datenbank oder nach einem Update mit neuen Spalten können alle Prozesse bis auf einen mit already exists-Fehlern stoppen und neu starten. Spiel so ein Update mit einer Replica ein und skaliere danach hoch.

Socket.IO braucht einen Adapter

WebSocket-Verbindungen hält jeweils ein Prozess. plugin-io lässt mehrere Prozesse mit dem Postgres-Adapter (LISTEN/NOTIFY) oder dem Redis-Adapter als einen Socket.IO-Server arbeiten, und Clients verbinden sich nur per WebSocket, weil Railway und pm2 keine Sticky Sessions haben. Jeder Prozess öffnet einen eigenen Verbindungspool: 8 Prozesse mit Strapis Standardpool von 10 brauchen 96 PostgreSQL-Verbindungen, also setz pool.max auf etwa 6, um unter einem Limit von 100 zu bleiben.
